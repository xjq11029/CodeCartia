# 业务发现有限模式实验实测

执行日期：2026-11-10。执行环境：Python 3.14.2，Windows 11（10.0.22621）。执行目录：`examples/prototypes/business-discovery/`，命令：`python verify.py`。本机使用 Python 标准库，没有新增第三方依赖，没有执行被分析工程。

本轮解决的是“只有业务展示与契约、尚未实证从原始源码形成场景步骤”的局部缺口：两个不同领域的原始源码现可自动产出入口、跨函数步骤、对象/条件和技术检查绑定。场景名称为源码锚点模板，未自动推断领域目标，也未把采购术语固化到提取器。

| 原始工程 | 自动场景 | 自动步骤 | 部分场景 | 独立文件预期比较 |
|---|---:|---:|---:|---|
| 模块化借阅 | 2 | 8 | 0 | 通过 |
| 单文件发布 | 2 | 9 | 2 | 通过；动态回调和未分类守卫保持未知 |

24 个评估器变异全部被拒绝；22 个源码/输出边界对照符合预期。详情及读取清单见 [verification.json](verification.json)，逐项实际结构与源码证据见 [library.json](library.json)、[publishing.json](publishing.json)。评估器核对了步骤与调用、实参映射与完整调用路径、对象与检查、条件及顺序、来源指纹、原始坐标与 AST 锚点，不能靠空输出、假候选、无关证据或遗漏跨函数步骤通过。

根协调独立阅读发现并推动修正了三项实现问题：同一源码的重复读取可能导致旧 AST 使用新指纹；输出范围过宽可能覆盖原始输入；评估器最初未核对技术配置/契约指纹。现改为同次原始字节捕获、只写 `reports/*.json`、独立核对配置和技术指纹，并增加对应输入竞态及拒错对照。运行时曾遇 Python 3.14 临时目录 0700 ACL 与受限 Windows 令牌不兼容，现使用继承工作区 ACL 的唯一临时目录，并验证清理路径；当次旧临时目录已清理。

另一子代理的独立复核进一步发现整函数局部遮蔽、合法但无关的证据替换、缺技术依据、未核对实参映射/完整调用路径，以及同行同地址注册身份冲突。现采用 symtable 预扫描整个函数的局部名字，已分类检查强制核对其原始 AST 与技术依据，独立预期明确冻结锚点、实参和路径，注册身份包含完整行列范围；上述反例均已纳入错误结果变异及原始源码对照，不以仅调整当前样例答案消除问题。

最后复核发现验证器辅助报告写入口仍可能跟随链接，现与 CLI 统一使用 `report_io.py`，保留原始路径并拒绝逐级父目录及最终目标的链接。真实 Windows 目录 junction 的父目录/最终目标各经 CLI 和验证器拒绝，共 4 个对照，临时哨兵均未被覆盖。没有用真实 expected/inputs 作链接目标。文件 symlink、其他平台及并发替换链接的竞态未实测，不宣称完整文件系统隔离。

结论仅适用于 [SPEC.md](../SPEC.md) 的有限 Python 模式和显式合成技术 API。`complete=true` 是有限范围的展开完整性；所有具体授权判定仍为 unknown。检查绑定描述先前检查与当前对象的源码调用关系，字段赋值不等于存储成功。没有验证具体框架的策略引擎、真实身份认证、跨语言、动态数据流、跨入口归并、事务或真实业务运行。

预期文件和评估器在实现依赖上独立，均未作为提取输入；但与提取器同次交付，两个工程也是公开开发用例。它们不替代独立保留项目、完整 BS/AP 验收、M1 全语言事实核对、D05/D06/D08 冻结或 G1。后续应在独立工程上确认步骤划分和分类口径，并将真实框架 API 语义单独验证后再扩大支持。
