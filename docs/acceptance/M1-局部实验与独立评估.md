# M1 局部实验与独立评估

> 版本：0.1｜日期：2026-11-10｜用途：M1-04/06/07/08/10 的探索验证与复核入口；不冻结产品质量门槛

本文件把设计复审中的可行性风险落实到原始输入、提取结果和独立检查。所有公开合成输入均属于开发验证集；同一代理曾看到预期的实验，不能宣称是隔离保留测试或跨项目泛化证据。产品分项准入仍按[需求与验收追踪](M1-需求与验收追踪.md)执行。

## 2. 分离提取、真值与评估

1. 提取器只读取登记的原始源码、技术配置和必要语义输入，不读取 expected、评估报告或故障注入答案，不执行被分析项目。
2. expected 按源码及明确技术语义独立编写，引用真实文件/声明/调用点。配置可登记实际入口注册或技术检查 API，但不能直接列出预期场景、步骤关系和角色权限答案。
3. evaluator 独立读取 actual 与 expected，按实验规格的语义键比较；场景名可以是入口锚点模板，不以自然语言字符串相似度代替结构正确性。
4. 对声明范围内的缺失、额外目标、错误入口/对象/主体绑定分别报差异；空输出不能通过，未知不能当作确定结果，重复记录不能掩盖错误。预期为 unknown 的输入另行核对原因和范围。
5. 对 actual 人为删除必经步骤、加入错误候选、换绑对象/入口或修改版本，评估器必须失败；这些变异只进入评估侧，不成为提取器输入。评估器若放行错误输出，先修评估器再报告识别结果。
6. 提取脚本、输入或工具版本改变后重跑报告，不能继续引用旧输入指纹的成绩。复核者核对实际源码和预期，不仅查看脚本退出码。

局部实验可采用精确集合匹配作为开发回归判据；这不是把产品 98%/90% 建议提前冻结。完整质量报告还须给每适配器/模式的样本、项目家族、分母、未知/截断和置信依据。

## 3. 场景发现的探索边界

无充分跨入口业务证据时，每个已识别入口保留独立场景骨架；共享函数只形成多场景引用，不凭连通性归并。步骤按可复核调用/检查/对象操作锚点构建，保留入口和参数绑定。该保守模式需显示“场景归并未判断”，不能据此宣布两个入口业务目标必然不同。

授权分类以实际技术检查语义及其挂载/调用为依据；函数名、异常文案、角色名或行业惯例都不足以证明。无法区分普通校验和授权时保留未分类检查，不补造 allow/deny。仅有检查点绑定也不等于已经求出完整授权结果；策略求值、跨服务身份、事务/持久化和完整路径要分别验证。

至少比较不同领域和不同代码组织的输入，并用同一提取器运行。公开合成两例用于发现写死假设，不构成项目家族隔离后的泛化结论。后续首版模式仍由 D05/D06/D08 根据实测与独立项目决定。

## 4. 真实项目加载的验证入口

在现有只读输入实验之外，M1-04/08 还须按候选加载路线完成以下实验后，才能关闭“取得真实语义而不执行目标工程”的风险：

| 输入 | 必须观察 | 失败判据 |
|---|---|---|
| Java 含构建脚本、profile、依赖和已有生成源码的项目 | 静态元数据/显式 classpath 取得方式、实际读取及进程启动记录 | 求值目标脚本、下载依赖；缺上下文却声称绑定完整 |
| C# 含导入、TargetFramework、任务/生成器配置的项目 | 显式引用路径与候选 project loader 的边界分别测，记录已禁用与未知能力 | 仅凭内存 Compilation 通过就声称 MSBuildWorkspace/真实加载安全 |
| C/C++ 编译数据库、响应文件与插件选项 | 只将命令作为数据；递归参数输入登记、允许参数范围和诊断 | 执行 shell command、加载未允许插件、未登记输入仍静默取证 |
| Python/JS 含顶层副作用与动态配置的项目 | 原始文件只解析、不导入；缺失动态配置明确诊断 | 为取得配置执行目标模块；哨兵副作用发生 |

这是待执行的验收规格，不是新项目加载器实现。工具缺失时记录缺失与替代路线，不通过改成普通源码小样例而标“项目加载通过”。

## 5. 推进顺序

M1-06 先交付有版本的预期和评估器草案；M1-04/07 用探索模式运行并反馈；M1-05/10 修订模式与预算，随后 M1-06 重跑对应版本，M1-09 才汇总冻结。各阶段的草案版本与冻结产物分开记录，避免把相互反馈误当成必须等待对方全部完成。

R11/R12 的参考模型检查、业务有限模式实验和已有语言局部输出都只更新各自实验状态。全部目标语言、真实框架、完整协议传输、项目加载、跨平台/布局/性能及独立准入仍按 G1 清单逐项核对。
