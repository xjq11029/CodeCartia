## 1. 使用方式与范围

本清单按已确认的业务组织原则，将“业务场景 → 步骤/动作 → 业务对象/业务规则”作为主线，在每一步附参与者、实际系统角色映射、授权条件、资源/数据范围、入口及检查点。稳定的 BC/AC 条目分别追踪场景事实及步骤中的授权关系，不代表两条并列产品主线；角色视图只是对同一组场景关系的跨场景反查或筛选。条目 ID 用于追踪需求，不能代替 M1-10 的模式 ID 或评估器真值 ID。语言与框架的目标范围另见[语言框架与输入覆盖清单](M1-语言框架与输入覆盖清单.md)。

按 2026-11-12 用户确认的 [D13](../decisions/D13-初版语言验证范围.md)，本清单的 M1 与首版验证只要求 JS/TS（含前端、Node.js、Next.js）和 Python 的适用模式。Java、C#、C、C++ 及 Spring/ASP.NET 的真实语义、业务和授权模式验证整体延后，不阻塞初版 G1/G3/G6，也不计为通过。BC/AC 编号与通用业务模型保留；首版步骤绑定、身份/策略判定、独立准入和未知边界要求不降低。

角色、权限和策略保留独立实体以便多个场景/步骤复用，关联上保留各自入口、主体和数据条件；不强制一角色一场景，也不将同一角色在不同场景的允许、拒绝或未知合并成统一结论。未能关联到业务步骤的权限声明保留“未关联/待核实”、独立证据与查询范围，不补造场景；无角色或未发现检查不推导匿名允许。授权条件与业务规则、状态变化及业务成功分别判断。

所有 BC/AC 条目的**产品目标均已确认**；具体“适配器 × 框架/授权引擎版本 × 模式 × 输入条件”的支持单元、预算和独立准入仍待原型验证及冻结。表中的模式组来自设计要求，不表示所有语言具有相同语义，也不承诺任意自定义引擎、外部策略或动态业务都能完整求值。已确认能力遇到困难须记录并向用户提出，不能直接改为“不适用”以绕过验收。[设计 §5.4][DES]、[推进 §4.4][PLAN]

本轮登记责任角色，不虚构已经到岗的人员或持续投入。每项由对应语言/框架适配负责人取得事实，由业务/权限集成负责人组合，由质量复核负责人独立核对；主协调者维护依赖和未决问题。具体执行人及并行投入由后续任务分派记录关联 D01。

以下输入均是被分析工程的原始源码、已存在配置或允许范围内的语义输入，读取遵守设计 §9 的只读边界。业务文档、测试、AI 解释及运行观察是可选来源，按用途独立登记。独立标注答案不得进入分析输入；不为补齐权限结论主动调用目标接口、运行目标工程、查询外部策略服务或收集真实凭据。

## 4. 确定结果对照与变化序列

以下对照沿用样例规格，属于 **M1-06/07/10 待制作及执行要求**。指定主体、角色、对象和策略都是合成输入，不是产品内置业务规则或所有项目的默认授权惯例。测试原始源码/配置必须实现这些事实；预期图与下表答案不得注入分析器。

| 对照及覆盖条目 | 冻结前须制作的原始依据 | 指定预期 / 变化序列 | 独立反例与限制 |
|---|---|---|---|
| [AP02] P4、R10；AC05/06/07/14 | 同一已认证 u6=manager+readonly/T1、同一 r2、完整绑定的认证→有序角色策略→租户→非本人检查链；两规则及目标工程实际读取的顺序配置/加载/first-applicable 实现 | 只交换规则顺序：O-allow-first 条件允许，O-deny-first 拒绝。记录首条命中、策略内部短路及后续必要检查 | 无匹配按该合成策略明确默认拒绝；u6 对跨租户 r4、u4 对自己的 r4 仍由后续检查拒绝。缺组合语义的 AP02-N1 另报未知 |
| [AP04] P2、R10；AC01/09/10/14 | u2 生产同一 approve(id=r2)；同一下游已挂载完整策略与资源；原始用户验证/绑定及服务主体绑定两个实现、实际加载的身份模式配置；独立保留传输身份和有效主体 | 只切换身份模式：I-forward-user 在验证成功条件下绑定 u2 并允许；I-service-subject 绑定无 manager 的 svc-approval 并拒绝。独立 HTTP 路径保持自身条件允许 | 原始身份验证/绑定输入缺失的 AP04-N3 才是未知；不因生产者 u2 或消息自报字段继续授予；不把允许视为审批已提交 |
| [AP06] P2；AC06/12/14 | 从完整 AP02 有序变体开始，冻结同一查询及其角色/资源/策略实现，登记顺序配置依赖 | O-allow-first→O-deny-first→O-allow-first，得到条件允许→拒绝→条件允许；每步增量与同输入全量等价 | 语义比较必须保留首条命中、短路范围、后续检查、判定和证据；重算前旧矩阵/解释显示过期 |
| [AP06] P3；AC09/10/12/14 | 从完整 AP04 身份变体开始，冻结同一消息查询、下游策略/资源及验证/绑定依据，登记身份模式依赖 | I-forward-user→I-service-subject→I-forward-user，消息路径条件允许→拒绝→条件允许；每步增量与同输入全量等价，HTTP 保持独立条件允许 | 不只改主体标签而复用旧授权；比较有效主体、检查链、判定、来源、证据；身份依据缺失/重新出现另纳失败查询对照 |

基准冻结时还须覆盖 AP02 的 D/A、AND/OR 与继承变体，以及 AP03 无角色属性策略、AP05 匿名/未知、BS02 对象/事务与异常等正反例。完整小组不能以少量确定结果演示替代其余规格。增量对照只忽略快照 ID、时间戳及无语义顺序，不能忽略实际策略顺序、有效主体、证据、诊断、候选或完整性。
