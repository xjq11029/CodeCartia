## 1. 来源、状态与登记规则

本清单依据 [设计方案 v0.6](../CodeCartia-设计方案.md) §1.1、§4–5、§7、§9、§10、§12，以及 [推进方案 v0.4](../CodeCartia-推进方案.md) §4、§6–7、§13。它将既有范围映射到稳定条目、必要输入、期望事实、责任角色与验证任务，不增加任意框架或动态行为的支持承诺。

按用户于 2026-11-12 确认的 [D13 初版语言验证范围](../decisions/D13-初版语言验证范围.md)，首版只验证 JS/TS（含原生 JS、Vue、React、Node.js、Next.js、JSX/TSX、HTML 与配置输入）和 Python。Java、C#、C、C++ 及 Spring Boot、ASP.NET Core 整体延后；相关条目保留为后续扩展，不阻塞初版 M1/G1、M3/G3 或 M6/G6，也不计为验收通过。已有 C# 局部实验作为历史探索保留。下文 M1 与首版的“各语言”“全部目标”均限于本次首版范围；保留范围内的框架、深度、质量和共同契约要求仍须逐项验证。

| 需求状态 | 含义 |
|---|---|
| 已确认 | 已确认的首版语言/源码输入目标或跨工程基本边界；实现与验收仍待完成 |
| 后续验证 | 用户已确认从初版验证范围移出的语言及专属框架/工具链；保留设计与追踪 ID，恢复时另行核对环境、模式和验收 |
| 设计列明，待覆盖冻结 | 设计提出的框架、子模式或版本路径；在 M1 落实可测试的版本和模式清单 |
| 候选方案 | 设计建议的实现工具或技术路线，须通过原型及决策选择 |
| 待决策 | 具体版本、协议客户端、绑定模式、平台组合或预算尚未确定 |

每个 LC 条目仅用于追踪，不能用它替代 M1-05 的逐语言传播细表或 M1-10 的业务/授权模式表。条目 ID 后续保持稳定，撤销或替换时保留理由与影响，不复用旧 ID。责任列表示职责，具体执行人和并行投入由 D01 登记；质量复核者独立核对真值。

以下表格中的版本与平台均引用 [D02：版本、系统与架构组合](../decisions/M1-待决策清单.md)；传播支持边界引用 D04，业务/授权支持边界引用 D05/D06，具体质量门槛引用 D07/D08，工程化选型引用 D10。所有引用均是待决策事项，当前没有冻结值。

## 5. 必要输入、目标平台与读取约束

### 5.1 输入登记约定

各 LC 条目需要由 M1-02/03/08 明确以下公共记录，具体 schema 在统一契约中制定：

| 输入类别 | 必须登记的信息 | 读取及失效约束 |
|---|---|---|
| 业务源码与静态配置 | 规范化路径、业务根、所属工程/配置、来源、指纹 | 目标源码只读；不启动应用或执行构建/配置脚本；配置变化、移动/删除和原先缺失输入出现均进入依赖追踪 |
| 必要语义输入 | SDK/系统头文件、package exports、类型定义、程序集/库元数据、存根、已有生成源码/头文件；登记根、来源、指纹与配置 | 业务索引排除不直接禁止必要语义输入；外部根须明确登记并核验，未登记/越界/缺失给出诊断，不自动下载或生成 |
| 业务文档、测试与策略 | 允许读取范围、版本、用途、来源及核实状态 | 可选文档不扩大默认边界；不取生产账号、令牌或运行外部策略补齐答案；标注真值与分析输入隔离 |
| 运行资源与环境映射 | 服务/进程、工作目录、文件空间、挂载、broker/命名空间、部署环境及映射来源 | 只读静态证据；同名或同路径不自动同一化；输入变化使候选、场景和权限依赖失效 |
| 二进制或生成输入 | 来源、原始/生成位置映射、可取得元数据及缺源码诊断 | 仅输出可证实边界；映射失败或无源码不造位置，不悄悄触发构建 |

路径与符号链接解析后仍须落在相应登记根中。M1-08 先验证 JS/TS、Python 的只读项目加载与动态配置边界；Java/C# 项目加载、构建工具求值及 Clang 插件/执行选项随对应语言留待后续验证，仍保留不直接执行命令字符串的约束。Web 读取业务根与外部语义证据 ID 的共同边界继续由 M1-02/08 定义。
