# CodeCartia 业务场景与权限验收样例

> 样例版本：0.3｜日期：2026-11-09｜对应设计：v0.6 第 10.5 节
>
> 状态：合成验收规格，尚未创建可执行样例、运行分析或取得验收结果。

## 1. 使用范围与验收约定

本文件将[设计方案](CodeCartia-设计方案.md)中的业务场景与角色/权限要求落实为 BS01–BS05、AP01–AP07 的正反例。后续按[推进方案](CodeCartia-推进方案.md)在 M1 制作原始输入、独立真值和评估器，再由相关实现阶段运行。以下采购业务、角色、数值和策略均是**测试指定输入**，不作为 CodeCartia 的内置业务规则或所有项目的授权惯例。

v0.3 明确以业务场景、步骤/动作、对象和业务规则组织结果：每步附参与者、实际角色映射、授权条件、数据范围和入口检查点。角色反查、条件矩阵与导出必须使用同一套步骤绑定；角色/权限可跨场景复用，未关联声明保留诊断，不能生成没有业务依据的场景。原有策略顺序和下游身份对照继续保留。

`F.*` 是逻辑证据标签，`r*`、`u*` 是合成对象标识；它们不指向当前仓库中已存在的源码、账号或数据。制作样例时须把证据标签映射到真实样例源码/配置位置和指纹。下面的事实描述用于规定待制作输入，预期图、人工真值和本文件的答案不得直接成为分析器输入。

所有案例默认采用冻结输入上的自动静态分析，关闭分析时 AI 与人工覆盖。AI 命名、文档解释和人工确认分别保存，依赖它们的后续推导继承来源。界面和导出必须区分：实现事实、业务含义解释、运行观察，以及确认、条件、未知、冲突、过期等状态。

授权结果限定到指定身份、入口、动作、资源、配置和条件。用“条件满足时允许”“拒绝”“未知”表达结论，同时记录认证要求、检查点是否已绑定和输入缺口。“未发现检查”是观测状态，不能自行等同允许或拒绝；“授权允许”也不等于业务操作成功。

这些样例只验证识别和解释，不收集真实账号/凭据，不主动探测目标服务，也不能据此宣称目标项目通过安全审计。具体框架/版本、支持模式、计算预算、样本量与门槛仍须 M1 冻结；现有 98%／90% 建议值不直接成为业务或权限质量门槛。

## 2. 基础合成输入 B0

### 2.1 场景、身份与对象

采购系统包含“提交采购申请”“审批采购申请”“查看采购申请”三个场景，提交和审批共用审计记录函数。业务文档称参与者为“申请人”“审批人”“观察者”，这些称谓需要显式映射，不能仅按中文名称推导系统角色。

| 输入类别 | 指定内容与证据标签 |
|---|---|
| 身份域 | `realm-purchase`；租户为 `T1`、`T2`。角色 ID 包含身份域，租户条件单独记录，来源为 `F.identity` |
| 合成主体 | `u1=employee/T1`、`u2=manager/T1`、`u3=readonly/T1`、`u4=manager/T2`。无默认角色继承，来源为 `F.roles` |
| 申请对象 | `r1=(owner:u1, tenant:T1, state:DRAFT, amount:1000)`；`r2=(u1,T1,SUBMITTED,1000)`；`r3=(u1,T1,SUBMITTED,6000)`；`r4=(u4,T2,SUBMITTED,1000)`。金额单位为测试指定的元 |
| 入口 | 提交、读取、审批路由分别绑定认证和对应授权检查；审批入口为 `POST /requests/{id}/approve`。绑定与顺序由 `F.route.*` 明确提供 |
| 前端 | 审批按钮使用 `manager` 做可见性判断，来源为 `F.ui.approve`；该判断不包含租户、所有者或业务状态检查 |
| 业务解释 | `F.doc.flow` 描述场景目的；源码/配置对应 `F.handler.*`、`F.policy.*`。文档解释与实现事实分别保留 |
| 工作流参与者绑定 | 目标工程通过 `F.workflow.load` 实际读取工作流候选人配置 `F.workflow.actor-bindings`：申请人绑定 `employee`，审批人绑定 `manager`，观察者绑定 `manager` 或 `readonly`。这是目标工程原始功能配置，不是交给 CodeCartia 的答案或人工分析配置 |

参与者绑定用于工作流候选人选择，不额外授予操作权限；后端仍执行第 2.2 节的实际检查。`manager` 因此对应审批人和观察者两种业务参与者，观察者也可映射到不同系统角色，必须保留这些多对多关系及其加载依据。

### 2.2 授权策略与业务规则

| 检查类别 | B0 明确指定的条件 |
|---|---|
| 认证 | 三个路由在动作执行前要求已认证；身份来自已绑定的认证上下文，不来自请求体自报字段 |
| 提交权限 | `employee` 拥有 `request.submit`，仅限同租户且申请属于当前主体，来源为 `F.policy.submit` |
| 读取权限 | `employee` 可读同租户自己的申请；`manager`、`readonly` 可读同租户申请，来源为 `F.policy.read` |
| 审批权限 | `manager` 拥有 `request.approve`，仅限同租户且申请不属于自己，来源为 `F.policy.approve` |
| 组合与默认 | 已绑定授权检查对适用允许规则取任一满足；没有允许规则满足时拒绝。B0 不包含显式拒绝规则，也不定义角色继承。该默认只适用于这些检查覆盖的范围 |
| 提交业务校验 | 对同一个申请对象，要求状态为 `DRAFT`、金额大于零；在有明确提交成功依据的条件路径上，持久状态为 `SUBMITTED`，来源为 `F.handler.submit`、`F.commit.submit` |
| 审批业务校验 | 对同一个申请对象，要求状态为 `SUBMITTED`、金额不超过 5000；不满足时分别返回状态错误或金额限制错误，来源为 `F.handler.approve` |
| 审批效果 | 状态更新为 `APPROVED` 与审计记录写入处于显式事务内，事务提交后调用回执发送；发送失败被捕获并记录，已提交审批不回滚，来源为 `F.tx.approve`、`F.receipt` |

此处金额门槛是业务规则；角色、租户和禁止审批自己的申请是 B0 明确放在授权检查中的条件。分类按实际实现位置和作用判定，不能把所有返回失败的判断都命名为权限校验。

上述状态与效果描述的是源码和配置证据支持的条件路径，不是已经观测到的实际执行。未取得同一对象的提交成功依据时，持久结果保持未知；成功分支不得覆盖提交失败或异常分支。

下述案例未声明的输入保持 B0 不变。每个变体拥有独立输入版本，不能把不同变体策略合并后进行评估。

## 3. 业务场景样例

### BS01：场景识别与共享代码边界

**输入与查询：** B0 的提交和审批入口均调用 `F.audit`，读取入口使用同一仓储；查询“系统有哪些采购场景，各自从哪里开始、作用于什么对象”。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| BS01-P1 | 分别组织提交、审批、读取场景，保存入口、动作、对象和步骤；从各步骤直接展开其业务规则、参与角色、授权条件、数据范围和检查依据；共享审计函数保留多场景关联 | 只提供业务流程与独立角色名单，要求使用者凭名称自行拼接；或只给函数列表，不能反查场景 |
| BS01-P2 | manager 角色在审批和读取场景中复用同一身份域内的实体；每条绑定分别保留动作、对象和检查条件，读取允许自己的同租户申请不改变禁止自审的审批条件 | 按角色把多个场景合并，复制成互不关联的同名角色，或把一个动作的数据范围直接赋给其他动作 |
| BS01-N1 | 共享审计与仓储保持公共实现关系，不产生“读取必然触发审批”或“提交后自动审批”的链路 | 按图的连通分量合成一个必然顺序执行的大场景 |
| BS01-N2 | 增加一个独立的定时归档入口后，将其作为候选独立场景；缺归档动作实现时保留缺口 | 因为没有页面入口而遗漏所有后台场景，或按任务名补出未实现动作 |

**证据与变更：** 入口和步骤引用 `F.route.*`、`F.handler.*`、`F.audit`；业务命名引用文档或保留推断来源。重命名公共审计函数不应合并场景；删除审批入口后，其注册事实及受影响场景完整性须重新计算。

### BS02：条件、对象状态、失败与补偿

**输入与查询：** 查询“u2 审批 r2/r3 会有哪些业务结果；状态何时改变；回执失败怎么办”。使用对象 ID、调用上下文和值版本区分每次读取与写入。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| BS02-P1 | r2 在授权与业务条件满足、事务成功提交的路径上由 `SUBMITTED` 变为 `APPROVED`；标出事务提交依据和回执步骤 | 只看到内存赋值或仓储调用就宣称持久状态已改变 |
| BS02-P2 | r3 可通过 B0 的角色/数据范围授权，但业务金额校验失败，输出相应错误且不进入状态写入 | 把金额失败归结为没有 `request.approve` 权限 |
| BS02-N1 | 事务提交失败的路径不报告审批已持久成功；回执发送失败的路径保留已提交审批和失败记录 | 把任何 `catch` 都解释为已完成补偿、回滚、重试或通知成功 |
| BS02-N2 | 变体读取 r2 状态却写入 r4 时，不生成“r2 已批准”的状态转换；对象别名无法确定时标记未知 | 将不同申请或不同值版本的读写拼成一个业务状态转换 |

**证据与变更：** 引用业务检查、对象绑定、写入、事务提交及错误处理位置。仅有回执调用而缺少发送实现时，不承诺送达；增添真正的重试/补偿实现后才更新相应步骤，旧解释标为过期并重算。

### BS03：误导命名、过期文档与关闭入口

**输入与查询：** B0 增加“自动付款”文档段落及名为 `paySupplier` 的空占位函数；另有退款处理器仅在已关闭的功能开关下注册。查询“该配置已实现哪些可进入的业务”。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| BS03-P1 | 已注册且有处理事实的采购场景显示对应实现证据；退款场景显示条件注册及当前配置未启用 | 把有源码的所有函数都标为当前配置已启用功能 |
| BS03-N1 | 自动付款说明保留为文档声明；空占位函数不能支持“已完成付款”，显示证据不足或冲突 | 根据函数名或旧文档生成完整付款链路 |
| BS03-N2 | 没有运行证据时，不能从入口启用推出生产环境有人使用、支付成功率或执行频率 | 将代码可进入条件当成实际发生事实 |

**证据与变更：** 文档、命名线索、注册配置与源码事实分开。开关从关闭变为开启后重新分析入口和场景，不复用旧可用性；只改文档不能改变自动提取的实现事实。

### BS04：双向映射、来源与快照失效

**输入与查询：** 从“审批申请”进入金额规则、实现和证据；从 `F.audit` 反查参与的场景。另在人工覆盖层给审批场景补充“需部门经理复核”的说明。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| BS04-P1 | 两个方向均保留场景 ID、步骤、关系、源码/配置证据与快照；共享函数返回全部有依据的场景关联 | 一个函数只能属于一个场景，或业务说明无法追到具体依据 |
| BS04-P2 | 删除审批路由注册后更新该入口的场景可进入状态、步骤授权绑定与角色反查；manager、共享审计及其声明证据仍保留，读取场景的既有角色关系不变，失去全部业务关联的声明进入未关联诊断 | 移除一条场景绑定就删除共享角色/策略或其他场景的关联，或者反查仍返回旧入口为当前可进入 |
| BS04-N1 | 人工复核说明单独显示，依赖它生成的步骤继承人工来源；自动结果仍没有该额外步骤 | 人工补充后将整个场景及其新增推导重新标为纯自动 |
| BS04-N2 | 源码规则由 5000 改为 3000 后，旧规则、场景说明和相关问答标为过期，更新结果采用新证据 | 继续展示旧阈值却使用新快照标签 |

**证据与变更：** 对源码、配置、文档、规则及人工覆盖分别记录依赖；删除共享审计调用后，移除对应场景关联，仍保留其他独立证据支持的关联和历史注释。场景归并、拆分或入口解绑时，主视图、步骤条件和角色反查同步更新；已存在的声明与业务关联分开比较，增量结果与同输入全量结果等价。

### BS05：无 AI 运行与独立业务验收

**输入与查询：** 对同一 B0 生成自动、分析时 AI 解释、人工调整三个结果视图；由独立复核者预先标注场景、关键规则、异常及证据。查询“各场景做什么、何时失败、修改哪里”。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| BS05-P1 | 关闭 AI 后仍能查看自动提取的场景入口、流程、条件、角色/权限关联、证据及明确缺口；自然语言含义不能确定时保留待核实 | 将未配置 AI 视为所有静态场景浏览不可用 |
| BS05-N1 | AI 虚构“金额超限自动通知财务”的说明被标为无依据，不能进入自动确认结果；人工补齐不能提高自动分数 | 用模型自己的总结作为真值，或用人工修正后的输出替代自动基线 |
| BS05-N2 | 必需场景、规则或异常分项缺标注/门槛时报告未完成验收；有运行证据也只作用于其版本和观测范围 | 沿用关系识别的汇总高分宣称业务理解全部通过 |

**证据与变更：** 记录输入、标注、评估器、模式及解释模型版本；模型切换不改变冻结自动事实。开发/规则生成代理不可读取保留测试；此公开合成规格属于开发用例，不冒充独立保留集。

## 4. 角色与权限关联样例

### AP01：业务参与者、系统角色、认证与前端可见性

**输入与查询：** 业务文档出现“审批人”；u2、u4 都具有当前身份域的 `manager`，前端均显示审批按钮；查询“谁能审批 T1 的 r2，为什么”。

| 用例 | 预期输出 | 禁止结论 |
|---|---|---|
| AP01-P1 | 依据已加载的 `F.workflow.actor-bindings` 显示参与者与系统角色的多对多映射；u2 在 B0 授权条件下允许审批，业务前置条件另列 | 仅凭“审批人”一词自动建立任意系统角色绑定，或将候选人映射当作权限授予 |
| AP01-N1 | u4 按前端逻辑可见按钮，但后端同租户检查拒绝审批 r2；u3 已认证仍无审批权限 | 按钮可见或登录成功即代表后端允许 |
| AP01-N2 | 新增 `realm-external/admin` 与 `realm-purchase/admin` 时保持独立；没有映射不得传递权限 | 因角色名相同把两个身份域的 admin 合并 |
| AP01-N3 | 变体仅将前端展示开关关闭，u2 看不到审批按钮；后端路由与 B0 策略不变，u2 对 r2 在授权条件满足时仍允许。并列显示 UI 隐藏与后端条件允许 | 按钮隐藏即代表后端拒绝，或把未显示入口当作后端路由未注册 |
| AP01-N4 | 删除参与者绑定配置且无替代实现依据，仅保留业务文档称谓和系统角色时，分别展示两类对象，映射保持未知；加载关系不可确认时亦保留缺口 | 按名称、组织惯例或后端有 manager 检查就补出完整参与者映射 |

**证据与变更：** 分别引用业务文档、工作流配置及其加载、角色定义、UI 判断、认证、路由绑定和后端策略。删除 UI 判断只改变可见性证据；不应移除仍生效的后端授权限制。删除或修改参与者配置使映射与派生场景说明失效，不抹去独立存在的后端角色检查。

### AP02：继承、多角色与策略组合

**输入与查询：** 为本组提供独立策略变体，均明确检查绑定及执行顺序。查询“同时具有 employee、manager 或 readonly 的主体能执行哪些动作”。

**有序策略变体输入：** `O-allow-first` 与 `O-deny-first` 是独立于 D/A、AND/OR 的一组对照，只替换 B0 审批授权中的角色判定部分，不保留另一条可绕过该判定的 B0 审批允许路径。两者使用相同主体、资源、策略实现与挂载，仅交换目标工程实际读取的 `F.policy.approve.order` 中两条规则的顺序；该配置的加载及执行依据为 `F.policy.approve.ordered`，完整检查链由 `F.route.approve.ordered` 绑定：

- 本组查询中的 `u1`、`u4` 和新增 `u6=manager+readonly/T1` 均处于 `realm-purchase` 的已认证条件分支，角色和租户取自已验证身份上下文；无额外继承或授予。资源使用 B0 的 r2、r4，按路由 ID 读取并绑定到同一申请对象。

## 5. 后续执行与结果记录

制作可执行样例时，每个用例登记：ID、项目家族、原始输入版本、逻辑证据到源码/配置的映射、分析模式、查询上下文、独立预期、实际输出、差异、状态及复现步骤。查询中的合成主体属性只用于实例化已取得的策略，不允许把“应允许/应拒绝”的真值作为配置注入。

验收分别报告场景识别、关键步骤、业务规则、对象/状态、异常处理、角色/权限/绑定关系、条件判定和证据。权限判断中的**错误允许与错误拒绝分别计分**；未知、缺输入、截断及条件尚未求值单独报告，并按冻结支持范围处理遗漏。业务规则或权限分项失败不能被普通引用关系的大样本抵消。

这些公开合成案例用于开发和契约回归。独立保留项目按项目家族隔离，其源码与标注不进入规则生成或调参上下文；实际用户阅读验证需让不了解实现的参与者回答“谁能做什么、在哪些条件下、失败怎么办、依据在哪里”，核对答案和误解。
