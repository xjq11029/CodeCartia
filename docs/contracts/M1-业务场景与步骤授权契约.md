### 1.1 有序策略的确定结果

沿用 AP02-P4 的完整独立输入：已认证 `u6=manager+readonly/T1`，同一对象 r2 的租户 T1、所有者 u1；角色来自已验证身份域。`F.policy.approve.ordered` 实际读取顺序配置，明确采用 `first-applicable`，无匹配默认拒绝。检查链为认证→角色策略→同租户→非本人；任一拒绝终止动作。该变体替换 B0 的角色判定，不保留绕过它的另一授权路径。

| 输入版本 | 有序策略及首条命中 | 策略内部短路与后续层 | `decision` / 条件 |
|---|---|---|---|
| O-allow-first | manager→allow 在前，readonly→deny 在后；首条 manager 匹配 | readonly 规则为 `not_evaluated`；同租户、非本人检查仍继续且满足 | `allow`，限上述认证、主体、入口和对象条件 |
| O-deny-first | 两条规则仅交换；首条 readonly 匹配 | 后续 manager 规则及后续授权层不再进入，注明拒绝终止范围 | `deny`，拒绝依据为首条匹配规则 |
| O-allow-first / u6 对 r4 | 角色策略仍命中 allow；r4 租户 T2 | 继续到租户检查并拒绝；不是角色策略内的拒绝 | `deny`，依据实际租户层 |
| O-allow-first / u4 对自己的 r4 | manager 允许，主体与对象同租户 | 后续非本人检查拒绝 | `deny`，依据实际所有者层 |
| 任一有序版本 / u1 对 r2 | 两条角色规则均不匹配 | 明确执行该策略的默认拒绝，不进入业务动作 | `deny`，依据该范围的默认语义 |

仅删除组合函数/加载依据或使用尚不支持的解释器版本，是 AP02-N1 的未知输入，不得混入上面完整变体。按冻结支持模式验证时，给两个完整变体相同结果或始终 `unknown` 均不满足确定结果对照。这里描述条件化静态执行路径，不证明规则在某次运行中已执行。

### 1.2 有效身份的确定结果

沿用 AP04-P2：同一生产者 u2、同一消息 `approve(id=r2)`、同一下游完整策略与挂载，两种身份实现均存在；只切换实际加载的 `F.identity.approval-mode`。消息传输使用服务身份。u2 是同身份域已认证用户、租户 T1、仅有 manager；`svc-approval` 是已认证服务、租户 T1、角色集合明确为空，没有额外授予或继承。下游策略要求同身份域已认证、manager、同租户且非所有者，任一失败拒绝；资源由消息 ID 从仓储读取，不采用消息自报属性。

| 输入版本 | 身份取得与绑定依据 | 消息入口有效主体与 `decision` | 独立 HTTP 入口 |
|---|---|---|---|
| I-forward-user | `F.identity.approval.verify` 验证原始用户身份材料，并在验证成功分支绑定用户 | u2；列明认证/验证成功及资源条件下 `allow` | 按自身认证和检查链，仍为条件化 `allow` |
| I-service-subject | `F.identity.approval.bind-service` 绑定已认证服务主体，不合并生产者角色 | svc-approval；因明确没有 manager 而 `deny` | 同上，消息身份配置不改变它 |
| AP04-N3 的独立变体 | 仅验证或有效主体绑定的必要实现输入缺失 | 有效主体及授权 `unknown`，列出缺失输入；不得选定 u2 或 svc-approval | 自身输入完整时继续保留条件化结论 |

`producerSubjectId`、`transportSubjectId`、`effectiveSubjectId` 分别存储；验证成功是路径条件及证据，消息字段不是验证依据。补齐相同版本必要输入后，未知变体才可恢复条件化允许。授权允许不证明业务校验、事务提交或回执成功。

| `BusinessStep` | 场景、入口绑定、动作引用、业务前置条件、参与者关系、授权绑定、正常/异常出口 | 同一动作在多个场景或入口中的步骤绑定各自保留；共享函数不证明步骤间顺序 |

| `BusinessObjectBinding` | 业务对象、上下文、读取/参数来源、符号/别名/值版本及确定性 | 对象概念、静态操作对象及查询实例分别关联；别名未知不确认跨步同一性 |

| `StateOperation` | 同对象/字段、前后值版本、阶段、路径条件、事务/写入关系、`storageBoundaryId` 与耐久性证据引用 | 使用 §4 的阶段证据；不能由单个赋值产生已持久成功或运行观察，内存仓储提交不等于数据库/磁盘耐久性 |

结构关系至少表达：能力包含场景、场景通过入口绑定包含步骤、步骤引用动作、动作操作对象/受规则约束、参与者参与步骤、步骤引用授权绑定、步骤/动作实现于代码。步骤流程关系记录分支、顺序、调用、异步发起或异常出口及其依据；只有已支持控制流/数据流能证明的关系才确认。图的阅读次序不充当执行时序。

同一代码符号可实现多个动作或参与多个场景，同一场景也可由多个代码位置实现。两个方向均引用同一关系 ID；步骤源码导航和代码反查不能分别维护不一致的映射。

## 4. 对象、状态与业务效果

`StateOperation.stage` 提议使用以下逐项类型，不作为自动升级序列；每种记录须有自己的依据，可在同一条件路径上关联。

| 阶段 | 所需证据 | 允许表达的结论 |
|---|---|---|
| `memory_assignment` | 同一对象/值版本的字段赋值和条件 | 该路径上的内存值改变 |
| `storage_write_request` | 有据绑定的写入调用、参数、作用对象和目标存储边界 | 向可见存储边界请求写入，不承诺成功或耐久性 |
| `commit_success_path` | 同对象写入、事务/提交实现或已验证框架语义、成功/失败分支与返回绑定、目标存储边界 | 在所列成功条件下，源码支持该边界内提交效果；耐久持久化另需相应语义证据 |
| `runtime_observed_commit` | 版本、环境、对象/主体、时间、目标存储边界与观测记录对应 | 仅该观测范围实际提交，不泛化到全部调用或更强耐久性 |

存储边界记录类型、资源身份及写入/提交语义；数据库/磁盘等耐久性结论保留独立证据和限制。现有 [采购示例](../../examples/purchase-demo/README.md) 的 repository 是同步副本后的进程内原子状态替换，仅能支持内存存储边界内的提交效果，不能作为数据库或磁盘耐久性验证。需要验证耐久持久化时，须以相应原始存储输入核对，不能用内存示例替代。

事务关系保存包含的写入、提交/失败出口及后续动作。捕获异常的事实不自动成为重试、补偿、回滚或通知成功；这些效果须另有调用和语义证据。异步发起、任务完成、外部接收及实际送达分别表达。后提交回执失败路径保留已提交条件事实；提交失败路径不复用成功状态。

业务结果引用具体步骤、对象、路径和规则，可分别记录前置校验满足/失败、正常/异常出口、各阶段效果与缺口；它不以授权 `decision` 作为成功值。业务条件未知也不自行改写已有完整授权结论，只影响对应业务结果和场景完整性。

## 5. 可复用主体、角色、策略与检查事实

| 记录 | 主题字段与引用 | 必须区分的含义 |
|---|---|---|
| `BusinessParticipant` | 业务名称/类型、参与步骤、名称依据 | 业务职责描述，不等于系统角色或有效主体 |
| `ParticipantMapping` | 参与者→主体/角色、适用步骤/入口、映射声明、实际加载关系、条件 | 候选人或职责映射不授予角色/权限；映射缺失不删除独立技术事实 |

| `Role` / 授予关系 | 身份域/原始角色标识、声明；主体取得、角色继承、角色/主体授予权限的条件 | 角色声明、角色取得、继承、权限授予是不同关系；同一有效主体才可满足多角色表达式 |
| `PermissionIdentifier` | 目标工程原始标识、动作/资源范围、声明/引用及授予关系 | 仅存在独立标识时建立实体；无标识策略不被迫创建权限节点 |
| `AuthorizationPolicy` | 原始判定表达式、效果、主体/角色/权限和资源条件、引擎/版本、组合/顺序/默认及支持状态 | 目标策略语义来自源码/配置或已验证版本规则；与 CodeCartia 识别规则组合不同 |
| `AuthorizationCheckpoint` | 入口/上下文、实际挂载与调用依据、层、时机、主体/资源、适用路径、策略引用、结果分支 | 声明存在、实际绑定、条件路径可达分别存储；HTTP 仅引用有据可达处理链上的检查 |
| `AuthenticationRequirement` / `VisibilityCondition` | 各自入口或 UI、表达式、来源和适用范围 | 登录、按钮/菜单/前端路由可见性与后端授权分别查询、显示和失效 |
| `DataScopeBinding` | 动作、对象集合/实例/字段、租户/组织/所有者等条件、查询/写入约束及属性来源 | 列表、详情、读取、写入各自保留范围；名称相同的属性不可替代实际读取来源 |

属性/资源关系策略允许角色和权限分支明确不适用，直接引用有效主体、策略、对象/动作及检查。角色/权限可多对多复用；不能复制成每个场景专属实体，也不能用相同实体 ID 合并不同绑定的条件。循环继承、动态授予、外部策略或尚不支持的组合保留边界与诊断，不静默选择结果。

## 6. 步骤授权绑定与未关联技术事实

`StepAuthorizationBinding` 是动作在业务与技术上下文之间的关联记录，不是被授予的权限或授权策略。其主题字段如下；来源、证据、解析状态与完整性仍用公共字段。

| 字段 | 含义与引用约束 |
|---|---|
| `scenarioId/stepId/actionId` | 已关联业务的稳定引用；三者结构须一致，不能引用另一场景的步骤作为同一绑定 |
| `entryBindingId`、`scope`、`callContextId` | 具体入口绑定及调用上下文/配置；同一内部动作有不同入口时逐一保存 |
| `objectBindingIds[]/resourceBindingIds[]/dataScopeBindingIds[]` | 作用对象、运行资源与数据范围；引用携带值版本和上下文，不由权限名称猜测对象 |
| `participantMappingIds[]/identityContextId/roleRelationIds[]` | 参与者映射、同一有效主体及实际角色取得/授予；无角色模式可显式不适用，缺输入必须诊断 |
| `permissionIds[]/policyIds[]/checkpointIds[]` | 有据权限/策略及实际覆盖该动作的检查链；上游检查可复用，但须证明当前入口、主体、资源与路径覆盖 |
| `coverageRelationIds[]` | 检查→当前动作的可达/调用/主体资源覆盖证明，引用 [调用上下文与 HTTP 分发契约](M1-调用上下文与HTTP分发契约.md)；仅同地址不是证明 |
| `conditionIds[]` | 该业务关联及检查适用的入口、主体、对象、配置/路径条件；业务前置校验另存，不能折叠为授权授予 |
| `businessAssociation` | `linked\|pending\|unlinked\|conflict`：有据关联、待补齐、在声明范围未找到关联、存在归属冲突；不代替 `resolution` 或 `decision` |

有效关联的 `linked` 绑定具有可核对的场景/步骤/动作引用。部分证据支持的候选关联可保存为 `pending`，引用已存在的候选业务实体并列出缺口。完全没有业务引用时，原始声明/授予/策略/检查保留为 `TechnicalAuthorizationFact`，并通过单独关联诊断表达 `pending` 或 `unlinked`，不创建空场景或虚构步骤填字段。

未关联诊断记录原技术事实 ID、已知技术关系、搜索范围、成功/失败查询依赖、输入完备性及缺口。输入未齐只能说待补齐；`unlinked` 仅说明在声明扫描范围未建立关联，不说明权限不存在、不适用、永不可用或动作一定允许。后来出现入口/动作证据时建立真实绑定并重算；原始技术事实的身份不因业务归属变化而改变。

## 7. 授权判定、条件与检查轨迹

`AuthorizationEvaluation` 针对一个绑定/技术路径与一个指定查询上下文，不对角色或整个场景给单一永久结论。

| 字段 | 含义 |
|---|---|
| `bindingId` 或技术路径引用、`queryContextId` | 查询对应的场景步骤（若已关联）、入口、配置、有效主体、动作、对象/资源及属性条件 |
| `identityContextId/objectBindingIds[]` | 实际求值采用的主体和资源绑定；合成查询值用于实例化已提取策略，不允许携带预期答案 |
| `decision` | `allow\|deny\|unknown\|conflict`；allow/deny 限完整有据的当前查询条件和路径，不能推成业务成功或跨入口结论 |
| `assumptionConditionIds[]/residualConditionIds[]` | 列明条件化结论的前提和未求值表达式；缺查询属性时保留表达式/缺输入，具体查询判定为 unknown |
| `conditionalCases[]` | 可选保存已支持策略下 `when` 条件对应的 allow/deny 分支，供条件矩阵解释；不把未实例化分支当作查询已允许 |
| `policyTrace[]/checkpointTrace[]` | 策略/检查 ID、有语义顺序、首条命中、适用条件、结果、后续转移、短路范围和证据 |
| `reasonIds[]`、公共完整性与来源 | 支持允许/拒绝、未知或冲突的依据；保留缺语义、未挂载、缺身份/资源、外部边界、超限及过期原因 |

轨迹中的规则或检查记录 `matched|not_matched|not_evaluated|unknown` 等求值观察及效果。`not_evaluated` 明确注明策略内部短路、已拒绝终止或路径未到达；不能删除未求值项后伪装为所有检查已通过，也不把未执行规则的效果求并/求交。该轨迹描述静态条件路径，实际运行轨迹另带运行来源。

允许/拒绝优先、AND/OR、首条匹配、覆盖、默认效果、层间继续和终止仅按目标工程实际语义求值。一个策略内部 allow 只完成其覆盖层；明确匿名/豁免也只作用于规定范围。仍有必要外部检查、未知分发/身份、资源绑定缺口或预算截断时保留 unknown。条件重叠的互斥依据无法消解时保留 conflict 及双方证据，不按显示优先级或 AI 解释选边。

“未发现检查”“声明未挂载”“未关联业务”“判定未知”分别表达。没有检查不能自行证明匿名允许或实际拒绝；不能把缺少业务关联的有据技术事实抹去，也不能为填充判定主动探测目标服务。授权结果和 §4 的业务校验/提交结果在步骤详情并列保留各自条件。

## 8. 主视图、反查、矩阵与导出的一致性

主视图沿场景→步骤/动作→对象/规则展开，并引用绑定和相同 AuthorizationEvaluation。角色反查沿有据主体取得/授予或参与者映射返回这些绑定；参与职责和实际授权关系标明类型，不能把映射结果直接计为授权允许。按权限/策略/代码反查也返回相同关系 ID。

反查行及矩阵单元至少保留：`snapshotId`、`scenarioId/stepId/actionId/bindingId`、入口/调用/配置、身份域/有效主体、对象/数据范围、条件、解析/业务关联/授权状态、来源、证据和完整性。缺业务关联的结果放入带技术证据的诊断，而不是伪造业务行。

AP07-P2 的 manager 对本人同租户 r5：读取绑定 allow、审批绑定 deny，各自对象和条件保持。AP07-P3 的同一 request.read 对列表和详情：权限实体复用，但列表集合范围与详情指定对象绑定分开。未知、条件分支或混合路径不能压成一个绿色“该角色可访问”。汇总可显示分类计数，不能取所有 allow 的并集替代逐动作条件。

往返导航以稳定关系/绑定引用回到原步骤；主视图、反查和矩阵是同一语义结果的投影。导出保留同样的快照、来源、条件、诊断及证据 ID；移除源码/绝对路径时注明被移除的载体，不能把人工说明或条件化结论转换为无条件自动事实。不可信文本/图标签/链接的呈现边界由公共契约和 M1-08 验证，不因证据已确认而允许执行内容。

## 9. 到达顺序、变化失效与共享事实

允许先索引角色/策略/检查，再取得场景及动作；处理中缺关联标 pending，最终按相同冻结输入与规则完成合并。先场景后授权或反向到达，最终绑定、未关联诊断、主视图、反查及矩阵须等价；不丢弃先到技术事实，不把 worker 完成顺序变成归属语义。

依赖与原子快照沿用 [资源、快照与规则组合契约](M1-资源快照与规则组合契约.md)。成功与失败的角色/策略/检查/业务关联查询都记录搜索范围和集合指纹，新增入口、声明或先前缺失输入可触发重新关联。

| 变化 | 直接及传递重算范围 | 共享事实与历史处理 |
|---|---|---|
| 场景归并/拆分、步骤/入口解绑、入口关闭 | 身份匹配、业务入口结构、步骤绑定、可进入条件、反查/矩阵/导出 | 不删除其他场景仍引用的角色/策略/检查；失去全部业务关联的原声明进入诊断 |
| 参与者映射/加载证据变化 | 对应映射、步骤参与说明及依赖它的派生内容 | 独立角色取得/后端检查保留；不把文案改名当成新的授予 |
| 角色授予/继承、策略/挂载/默认/范围变化 | 实际依赖的检查链、授权判定、步骤条件、反查与说明 | 删除一条推导后重新合并其他独立支持；重算前旧结果 freshness=stale |
| 仅交换有序策略顺序 | 首条命中、短路、后续层和判定及其全部投影 | AP06-P2：allow→deny→allow；有语义顺序进入指纹，不能归为无序集合 |
| 仅切换身份模式，或验证/绑定输入缺失及恢复 | 消息入口有效主体、检查判定及其投影；缺输入查询同步失效 | AP06-P3：allow→deny→allow；HTTP 依自身证据保留，缺身份变体为 unknown |
| 对象/状态字段、写入/提交/异常事实变化 | 同一对象绑定、业务规则/效果、依赖该属性的授权、场景解释 | 业务影响和授权影响分别沿真实依赖传播；不复用旧对象或提交事实 |
| 文档、AI/人工说明、识别规则停用或回退 | 受影响来源层的描述/关联/判定及传递推导 | 保留自动基线、独立来源和历史注释；覆盖层不提高自动成绩 |

相同当前输入、配置、分析器、有效规则组合、模式及预算下，增量/全量比较包含实体、步骤/入口、对象、条件、判定、轨迹、证据、来源、候选与诊断。只忽略快照 ID、时间戳和无语义输出顺序；不能忽略策略顺序、主体变化或缺口。输入混合、中断/部分结果及过期判定不得替换完整当前快照。
