# M1 worker 协议正反例与实验规格

> 草案版本：0.1｜`protocolVersion: 0.1-draft`｜`schemaVersion: 0.1-draft`｜日期：2026-11-10｜工作包：M1-03
>
> 状态：独立预期与待执行实验规格，未实现消息生产器、协议校验器、worker 或测试运行器。本文消息、计数与状态均为手工示意，未取得协议执行、各语言分析或产品验收成绩。

依据：[M1-03 任务](../progress/M1-任务清单.md)、[需求追踪](../acceptance/M1-需求与验收追踪.md)中的 REQ21/22/39/41，以及四份 [M1-02 契约](README.md)。逻辑字段对齐 [worker 与扩展协议草案](M1-worker与扩展协议.md)，预期先从源要求独立定义，再检查协议能否表达和验证。局部 `W-*` 编号只定位本附录，不新增 R/BS/AP 产品验收组。

## 1. 实验首先要区分的结果

| 观察层 | 应检验的事实 | 不能替代的结果 |
|---|---|---|
| 协商 | 协议、图 schema、扩展及所请求能力分别匹配；选定版本显式冻结 | 协议版本相同不能证明图字段或语言模式兼容 |
| 消息接收 | 包络/作用域合法、批次已暂存，重复消息可辨识 | `batch.ack` 不表示引用闭合、关系正确或快照已发布 |
| worker 终结 | 生产者声明 outcome、批次清单、计数及完整性 | `task.finished` 不自行决定宿主终态、整体语义完整或可见快照 |
| 宿主裁决 | 在同 attempt 的原子记录中决定完成、部分、取消、超时或失败；迟到消息不能推翻 | worker 壁钟、EOF、日志和处理先后不能直接覆盖宿主裁决 |
| 快照发布 | 所有必要生产者、输入一致性、引用/来源及语义完整性通过，整体原子切换 | 一名 worker 正常退出或批次数吻合不能代表全语言/业务准入 |

失败实验也应产生可核对结果：拒绝/隔离原因、宿主状态、已验证局部事实的保留范围、旧快照状态和未发布原因。只有“没有崩溃”或“控制台有错误文字”不算满足预期。

## 2. 受控消息输入与冻结前提

实验用宿主 H 与受控消息生产者 W；W 只模拟消息与故障，不从预期构造自动分析成绩。后续真实语义 worker 必须另从原始源码/配置产生事实，再由 M1-04/07 独立核对。

| 前提 / 指定值 | 约束 |
|---|---|
| `sessionId=s1`、`taskId=t1`、`attemptId=a1` | 正常序列的隔离键；重试使用新 attempt，重新启动使用新 session，不复用旧消息身份 |
| `snapshotId=snap1`、`scope.configId=c1` | 明确工程 p1、环境 env1、配置 c1；角色声明尚未绑定入口时显式保留未绑定状态，不解释为所有入口 |
| `analysisProfileId=ap1`、`inputManifestRef=im1`、`identityRegistryRef=ir1` | 均指已冻结的版本/指纹与来源视图；已登记输入、规则组合、模式、预算和共享元数据使用一致版本 |
| `sourceViewId=sv-static` | 正常序列是无当次 AI/人工依赖的自动视图；辅助来源实验另用显式请求的独立视图/任务，不向自动账本混入 |
| `allowPartial=true` | 正常合成任务明确许可结构合法的语义部分结果；这是指定实验值而非产品默认，W-S09 单独改为 false |
| 能力与扩展清单 | 每例明确“必需/可选”、声明/协商版本及支持范围；缺输入、缺工具与能力不支持分别记录 |
| 旧可见快照 `snap0` | 初始已发布完整结果，用于证明坏批次、取消、超时、部分结果不会替换；只有当前输入改变才将旧相关结果标过期 |
| 内容指纹 `fb1/fb2` | 仅本附录的符号标签；后续样例必须保存实际原始载荷、规范化规则/算法和实际指纹，不把标签当真实摘要值 |

本规格不选定 stdio/JSONL、socket、帧编码、hash 算法、窗口大小、超时或内存上限。逻辑字段与实验顺序可先审阅；传输相关实验在登记候选实现和具体探索参数后执行，参数属于实验配置，不直接冻结产品范围。

### 3.3 批次、引用、清单与背压

| 局部例 / 来源 | 操作或唯一变体 | 具体预期 | 失败判据 |
|---|---|---|---|
| W-B01-P / REQ21、REQ20 | 关系 r1 在 b1，所需 x/y/ev1/d1 在 b2；有效终结清单与实际两批一致 | b1 可暂存/ACK；b2 后引用闭合；总记录 5，按 kind 和清单分别核对；再进入宿主裁决 | b1 ACK 就发布完整关系，或因为前向引用立即删除 r1 |
| W-B02-P / REQ21 | b1 以相同 batchId/sequence/内容指纹重发 | 幂等回应，唯一批次和记录计数不增加；来源不复制 | 重复变成第三批、总数变 6 或新增重复派生 |
| W-B03-N / REQ21、R07 | 同 batchId 或同 sequence 重发不同内容/指纹；另有同 wireRecordKey 携带互不相同的内容 | 报告批次/版本记录完整性冲突，保留双方审计；不能按到达先后选真或继续完整发布。不同 revision 或独立 Derivation 的语义候选/冲突另按 R07 合并 | 只按逻辑 record ID 判所有输出损坏；去重掩盖同键差异，或最后写入覆盖底层事实 |
| W-B04-N / REQ21 | 只丢 b2，但 task.finished 仍声明 finalSequence=2 且清单有 b2 | 缺批次/范围诊断，清单与接收不一致；不得 sealed_completed 或发布 | 仅比较 finalSequence 最大值或只相信 worker 清单 |
| W-B05-N / REQ21 | 批次齐备，只修改终结的 recordCount/totalRecordCount/recordCounts 或 payloadFingerprint；各为独立变体 | 与实际暂存清单逐项比对，报具体差异；不修改已接收数据以配合 summary | 只验证总数或 worker 自报摘要，忽略分项/载荷不符 |
| W-B06-N / REQ21 | 数据已齐备但没有 task.finished，随后 EOF/进程退出 | 宿主失败/异常退出；数据可作为有据局部暂存保留，不能自行完成 | “最后一批已到”或 exit 0 当成 completed |
| W-B07-N / REQ20 | 完整清单中最终仍缺 r1 的一个必要本地目标/证据/推导 | 给出悬空引用及受影响事实；不得发布完整图或补造目标 | 自动生成空实体、去掉引用或将坏关系伪降为合法确认 |
| W-B08-P/N / REQ21、REQ22 | AnalyzeRequest.declaredExternalProviders 指定同 snap1 的另一个 producer/task；独立变体为错快照/未登记、provider拒绝/失败/取消/终结缺目标或等待期限届满 | 仅已登记依赖可暂存；清单可 sealed_manifest，等待外部引用时宿主仍 open/validating、可取消，整体发布前闭合；坏引用隔离，provider终止/缺目标或期限届满使受影响 attempt 有限失败并列出依赖scope，无依赖任务不受牵连 | 任意缺引用都猜作外部；一名生产者终结就整体发布；provider已终止仍无限等待或将全工作区无差别失败 |
| W-B09-N / REQ21、S01 | 登记的数据窗口耗尽，继续发送大批；同时触发 cancel/timeout | 背压及资源观察明确，不静默丢必需记录；取消/超时控制仍可被处理，受影响结果完整性受限 | 无限缓冲、丢引用继续完整，或控制队列被未 ACK 数据堵死 |
| W-B10-N / REQ21、REQ46 | 候选传输中分割、截断、错编码或超出登记帧范围；另有完整中文/空格/emoji 文本 | 合法分割能还原原始载荷；非法帧有诊断并不得注入事实；正常文本不被误丢 | 字节边界破坏内容指纹、按乱码猜原文，或把合法换行当普通日志 |
| W-B11-P / REQ21、R07 | W-B01 的 b2 再携带同 wireRecordKey、同内容的 r1，其载荷指纹改为 fb2-repeat，manifest 正确登记 5 条 | 传输按两个唯一批次中的载荷出现计数：b1=1、b2=5、totalRecordCount=6、Relation=2；合并后的唯一版本记录仍为 5，两种计数分别报告 | 用合并唯一数 5 检查载荷总数，或把合法跨批重现当重复批次失败 |

wireRecordKey 依主草案区分 kind、逻辑 ID、revisionId/版本锚点、来源视图和 scope；同逻辑对象的不同版本/独立推导不是同键异内容。W-B07 的损坏引用和语义输入缺失是不同失败：前者不能伪造结构补齐；后者可保留已有合法局部事实及缺输入诊断。合法 partial 的引用、schema 与来源也须可核对；协议损坏不通过改一个 complete=false 就变成可发布的合法结果。

### 3.4 终态、取消、超时与重试

| 局部例 / 来源 | 操作或唯一变体 | 具体预期 | 失败判据 |
|---|---|---|---|
| W-L01-N / REQ21、REQ22 | 已 ACK 一批后 worker 崩溃 | 记录异常退出和失去的范围，宿主封存失败；旧快照不被半批替换 | 进程消失当 completed 或复用不完整缓存 |
| W-L02-N / REQ21、REQ22 | 登记任务/空闲探索期限到达，worker 未响应；随后发送 late completed | 宿主 sealed_timed_out，迟到只审计；清理/重启行为留记录，不自行解除封存 | 最后 arrived 的 completed 覆盖超时，或只发 cancel 却无限等待 |
| W-L03-P / REQ21 | 宿主先接受上层取消并原子封存，再发 task.cancel；后到 task.finished completed/新批次或 worker cancel.ack=already_terminal | 宿主 sealed_cancelled；HostCancelResult 与 cancel.ack/worker outcome 分别记录，worker 本地“已终结”不阻止宿主裁决，后到数据不发布 | worker 宣称完成重新打开取消任务，或等待 ACK 才阻止发布 |
| W-L04-P / REQ21 | 所有校验已通过且宿主先原子封存完成；上层取消后来到达 | 保留 sealed_completed；HostCancelResult.status=already_terminal，通常无需向 worker 发送取消；已合法发布结果不回滚 | 用 worker cancel.ack 当宿主返回值；迟到取消抹去已发布结果或按 worker 壁钟重排裁决 |
| W-L05-P / REQ21 | task.finished 已收到但仍 validating，随后 cancel 在校验/封存竞争中先被接受 | sealed_cancelled，验证回调不得再次封存完成或发布 | 仅“收到 finished”就返回 already_terminal；异步验证后绕过取消锁 |
| W-L06-N / REQ21 | 相同终结重发；独立变体 outcome/清单变化；分别在 open/validating 与 sealed 后发送 | 同内容重发幂等、不二次发布；变化终结在未封存时 sealed_failed，在已封存时保留原裁决并诊断审计；重复取消不重新封存 | 变化终结在 open 时只记录不失败，已 sealed 被第二条终结改写，或重复发布两次 |
| W-L07-P/N / REQ21 | 相同 analyze 身份与冻结载荷重发；变体同 attempt 改输入/规则指纹 | 相同请求按协议幂等，不启动两个独立副作用；冲突载荷拒绝，变化需新 attempt 和相应 snapshot | 同隔离键悄悄启动两次，或让重试混合版本 |
| W-L08-N / REQ22 | 已 sealed_completed、尚未持久化/发布时，必要输入变化；另有存储事务失败变体 | 宿主执行终态仍 sealed_completed；撤销 publication 资格并隔离本次结果，记录发布失败/输入变化，旧可见快照保持（输入变化才标其相关证据 stale）；新任务使用新 attempt | 把 sealed_completed 逆转为 sealed_failed，或因执行已完成仍发布混合版本/未持久化结果 |
| W-L09-P/N / REQ21 | 明确协商的一个 worker 进程承载两个活动任务；其中一个已取消但停止期限届满，需要进程级强制结束 | 取消者保持 sealed_cancelled；同进程其他未封存 attempt 封存 failed 并记录关联进程/终止原因，已封存裁决不逆转；所有相关快照依赖受限。任务级停止只有实际隔离模型有据支持时单独验证 | 只报告取消者而让同进程其他任务假装继续运行；无隔离证据承诺只终止一个任务 |

宿主 HostAttemptRecord.decision、上层取消返回 HostCancelResult 与 worker task.finished.outcome/cancel.ack 分开记录；词表遵循主草案。取消与完成的结果以宿主同 attempt 的原子接受裁决为准。实验必须覆盖两种先后和“finished 已收、校验未完”的第三种窗口，不能只验证没有竞态的直线序列。执行封存不可逆，后续发布失败是独立结果，不改变既有裁决。

### 3.5 完整性、来源与业务组合

| 局部例 / 来源 | 操作或唯一变体 | 具体预期 | 失败判据 |
|---|---|---|---|
| W-S01-P/N / R01、REQ21 | 合法局部入口事实已确认，但下游摘要/必要语义输入缺失或预算截断 | 局部 resolution 保留，completeness 缺口和 affectedScope 传到相关链路；合法终结为 partial；相关完整链路/确定授权受限 | completed 或 ACK 将 complete=false 洗掉；未知默认为 deny/allow |
| W-S02-P/N / R05、Q01 | 显式辅助视图任务含人工/AI 依赖推导及独立静态事实；另以自动视图接收伪装 static 的辅助依赖变体 | 辅助视图保留各项完整来源闭包；自动视图拒绝伪装及受影响推导；传输成功不改变自动基线 | 原包络“static”覆盖依赖来源，或人工结果提高自动成绩 |
| W-S03-P / BS04、AP07 | 先角色/策略声明后场景绑定；交换到达顺序但原始事实与配置相同；另一声明始终无业务证据 | 最终同关系绑定、反查及未关联诊断等价，共享原始声明保留；无业务证据不造场景 | 暂未关联就删声明，或从权限名补业务；先到结果改变归属 |
| W-S04-P / R07/R09/R10 | 打乱各 worker/batch 完成顺序，保留载荷内相同注册/策略顺序和有效身份 | 协议搬运不改变有语义的载荷顺序/主体，后续分发/授权验证使用同样输入 | 用接收 sequence 代替路由/策略注册顺序，或按先到策略选结果 |
| W-S05-N / R02、REQ22 | 同路径源码、规则组合、模式/预算或身份登记任一指纹变化；旧 attempt 继续发完 | 旧版本不作为当前完整依据；重试冻结新版本并新隔离；变化的旧相关证据标 stale | 同路径等同同版本；新标题包装旧快照；只重算最终恢复点 |
| W-S06-P/N / REQ17、REQ21 | 必需 producer A completed，B partial/failed/不可用；其他输入不变 | 各生产者状态可查看，整体范围 complete=false，旧完整结果不被单线完成替换 | 多数 worker 成功就宣称整个工程/首版通过，或省略 B 的范围 |
| W-S07-P/N / R04、REQ21 | 技术空任务 finalSequence=0、batchManifest=[]、totalRecordCount=0；变体有数据却终结报空 | 真空任务可按协议终结并记录空范围；产品分项缺样本仍未验收；非空变体清单不符被拒 | 空数据自动“100%通过”，或零总计忽略已收批次 |
| W-S08-N / R06、REQ41 | 输入消息/规则/图标签出现未登记路径或构建命令 | 读取范围保持冻结，越界/缺输入有诊断，不执行/下载/生成 | 为让实验完整执行命令、导入用户模块或自动扩大读取根 |
| W-S09-N / REQ21、REQ22 | 请求 allowPartial=false；运行中才发现语义缺口，worker 回结构合法、引用闭合的 partial | 传输/schema 校验可以通过；严格完成条件不满足，宿主 sealed_failed、reasonClass=semantic_incomplete，有据局部材料独立保留，不能替换完整快照；提前已知缺口则任务拒绝 | 仅因 outcome=partial 就封存 sealed_partial、忽略严格请求，或将语义失败伪装为载荷损坏 |

W-S03/04 只定义协议不得损坏、提前裁决或丢弃原始字段的预期。真实场景/策略/身份分析与确定 allow/deny 对照仍须 M1-04/07 从源码和实际配置产生输出；受控消息不能代替这些分析。

## 4. 对齐字段的逻辑序列

下述为折叠了公共包络和完整记录内容的**逻辑消息示意**，不是线上帧、样例工程或分析器输出。省略字段在可执行样例中必须补齐；不可直接把示意文字交给协议接收器。

### 4.1 W-B01 正例与两个只改一项的反例

所有任务消息使用 §2 的隔离键和冻结版本。记录账本为：r1 是有 evidenceIds=[ev1]、derivationIds=[d1]、sourceId=x、targetIds=[y] 的公共 Relation；x/y 是 Entity 版本记录；ev1 是合法 Evidence；d1 以 x/y/ev1 为直接依据支持 r1。条件为空的含义、输入登记及来源/分析器/规则引用另在冻结元数据中明确，不由空列表证明整个工程无条件。

| 顺序 | 消息 / 核心字段 | 宿主应有观察 |
|---|---|---|
| 1–3 | W hello；H initialize 选择 protocolVersion/schemaVersion 与清单；W ready | 协商完成，尚无任务/业务结果 |
| 4–5 | H analyze(t1,a1,snap1,c1,ap1,im1,ir1)；W task.accepted | 创建隔离暂存区，HostAttemptRecord.decision=open |
| 6 | W facts.batch(batchId=b1,sequence=1,payloadFingerprint=fb1,records=[r1]) | 接收 1 条，前向引用未齐，暂存而非完整发布 |
| 7 | H batch.ack(b1,sequence=1) | 只确认接收状态，不解除最终引用/语义检查 |
| 8–9 | W facts.batch(b2,2,fb2,[x,y,ev1,d1])；H batch.ack(b2,2) | 唯一批次 2；records 共 5；本地必要引用闭合 |
| 10 | W task.finished(outcome=completed,finalSequence=2,batchManifest=[(b1,1,fb1,1),(b2,2,fb2,4)],recordCounts={Relation:1,Entity:2,Evidence:1,Derivation:1},totalRecordCount=5,completeness=完整声明范围) | 校验接收清单/计数/指纹/引用/来源及范围；尚不因收到消息自行发布 |
| 11 | 宿主原子封存完成；整体所有必要 producer 和快照门槛通过 | 该范围才可按快照契约原子发布；不是各语言/业务准入成绩 |

W-B04 只去掉步骤 8/9，仍用同一终结：宿主实际只收到 1 批/1 条，明确缺 b2/引用，不能完成发布。W-B05 只把步骤 10 的 totalRecordCount 改为 6：实际总数仍为 5，必须报告计数不符；不能复制 r1 或更改接收账本来配合终结。分项数、manifest 指纹或序列范围的独立变体按同样方法逐项对比。

### 4.2 W-L03/04/05 的宿主裁决顺序

| 序列 | 被宿主原子接受的先后 | 期望宿主终态 / 发布效果 |
|---|---|---|
| 取消先赢 | 上层取消 → HostCancelResult.accepted/sealed_cancelled → task.cancel → late task.finished completed | 保持 sealed_cancelled，late outcome 和 worker cancel.ack 留审计，不发布新结果 |
| 完成先赢 | task.finished → 全部校验通过 → sealed_completed → late 上层取消 | 保持 sealed_completed；HostCancelResult.status=already_terminal；合法可见结果不回滚 |
| 校验窗口取消 | task.finished received → validating → cancel/sealed_cancelled → validation callback | 保持 sealed_cancelled；回调必须再次核对裁决，不能封存/发布 completed |

消息日志保存接收顺序与宿主状态转移；worker 时间戳仅作为观察，不能用于重新判定取消与完成谁胜出。封存任务的数据仍可作为明确历史/审计记录保留，不能重新出现在当前自动事实视图。
